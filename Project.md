# QueryForge

QueryForge turns a database schema and a plain-English question into a SQL query — then actually runs that query against real data before showing it to you.

Most LLM-based SQL generators stop at the model's output: you get a string of SQL and you're trusting it's correct. QueryForge doesn't stop there. After Groq (in JSON mode) generates the query, an explanation, and the tables it used, [sql.js](https://github.com/sql-js/sql.js) — SQLite compiled to WebAssembly — executes that exact SQL in your browser against the sample data you provide. If the query is wrong, you get a real error or an empty result set, not just plausible-looking text.

That verification step is the core of this project. LLMs hallucinate column names, misjudge joins, and confidently produce syntax that doesn't run. QueryForge catches that before you copy a query into anything that matters.

It is a single static site — HTML, CSS, and JavaScript, no backend, no build step, no framework — designed to run as-is on a Hugging Face **Static** Space or any plain file server.

## How it works

```
┌─────────────┐   schema + sample data + question    ┌───────────────┐
│             │ ────────────────────────────────────▶│   Groq API    │
│   Browser   │                                       │  (JSON mode)  │
│ (this app)  │ ◀──────────────────────────────────── │               │
│             │   { sql, explanation, tables_used }   └───────────────┘
└──────┬──────┘
       │
       │  generated SQL + your pasted CREATE TABLE / INSERT statements
       ▼
┌──────────────────┐
│     sql.js       │   builds a fresh in-memory SQLite database,
│ (SQLite in WASM,  │   runs your schema, runs your sample data,
│  runs client-side)│   then runs the generated SQL
└────────┬─────────┘
         │
         ▼
  a real result set, or a real error — rendered in the browser
```

Two independent systems do two independent jobs:

1. **Groq writes the SQL and the explanation.** The app sends your schema, your sample data (if any), your question, and your chosen dialect to Groq's chat completions endpoint using JSON object mode (`response_format: {"type": "json_object"}`). The model replies with a JSON object shaped like `{"sql": "...", "explanation": "...", "tables_used": [...]}`. **Groq never executes anything — it only writes text**, and like any LLM it can be confidently wrong.

2. **sql.js is what actually runs the query.** When you click "Run query," the app spins up a brand-new in-memory SQLite database in your browser, executes your pasted `CREATE TABLE` statements, executes your pasted `INSERT` statements, and then executes the SQL Groq generated — showing you the genuine result set (or a genuine error) instead of asking you to trust the model's text output.

No data leaves your machine except what's sent to Groq for generation (your schema, sample data, and question). The actual query execution and verification happen entirely client-side.

## Features

- Plain-English question → SQL query, explanation, and a "tables used" list, generated by Groq in a single JSON-mode API call
- Defensive JSON parsing that handles markdown-fenced or slightly messy model output (stray text before/after the JSON, missing fences, etc.), with a clear error message if parsing still fails rather than showing nothing
- Live, in-browser query execution and verification via sql.js — no server, no database connection, no data persisted anywhere
- Dialect-aware generation for MySQL, PostgreSQL, and SQLite, with honest handling of the fact that live execution is SQLite-only
- Syntax-highlighted SQL output (highlight.js), one-click copy-to-clipboard, and a full reset button
- A results grid styled like a real database client's output pane — row-number gutter, monospace values, zebra striping — instead of a generic HTML table dump
- Readable, specific error handling for invalid API keys, rate limits, network failures, malformed model output, schema errors, sample-data errors, and SQL execution errors — each with its own message
- Buttons and a top progress bar disable/enable themselves automatically during generation and execution
- Responsive layout down to mobile, with a restrained, single-accent visual design (no decorative gradients or ambient animation)
- 100% static: three files, no backend, no build step, no dependencies to install

## Getting started

> Setting this up as a fresh GitHub repository (creating it, adding a license, first push, repo settings)? See [REPO_SETUP.md](./REPO_SETUP.md) instead — this section covers running the app itself, not the repo around it.

### Prerequisites

- A free [Groq API key](https://console.groq.com/keys)
- Any modern browser (Chrome, Firefox, Safari, Edge) with WebAssembly support
- Nothing else — no Node, no package manager, no build tooling

### Adding your Groq API key

1. Open `script.js`.
2. Find this line near the top of the file:
   ```js
   const API_KEY = "PASTE_YOUR_GROQ_API_KEY_HERE";
   ```
3. Replace the placeholder with your actual key, keeping the quotes:
   ```js
   const API_KEY = "gsk_your_actual_key_here";
   ```
4. Save the file.

### Running it locally

Because the app only makes outbound calls to Groq and to two CDNs, you can run it from almost any local static server. For example, from the project folder:

```bash
python3 -m http.server 8000
```

Then open `http://localhost:8000` in your browser. Opening `index.html` directly via `file://` also works in most browsers, though some browsers restrict `fetch()` or WebAssembly loading from `file://` URLs — a local server avoids that entirely.

## Usage guide

1. **Schema** *(required)* — paste one or more `CREATE TABLE` statements describing your database.
2. **Sample data** *(optional, but required to run queries live)* — paste matching `INSERT` statements.
3. **Your question** *(required)* — ask what you want to know, in plain English (e.g. "Which 5 customers have spent the most in total?").
4. **SQL dialect** — choose MySQL, PostgreSQL, or SQLite.
5. Click **Generate SQL**. Groq returns a query, a plain-English explanation, and the tables it used, shown with syntax highlighting.
6. Click **Run query** to execute that exact SQL against your pasted sample data using sql.js, and see the real result set (or a specific error) rendered as a table.
7. Use **Copy SQL** to copy the generated query to your clipboard, or **Clear all** to reset every field and start over.

## Dialect support and verification caveats

Groq will always write correct, idiomatic SQL for whichever dialect you select — MySQL, PostgreSQL, or SQLite — using dialect-appropriate identifier quoting, string/date functions, and clauses.

However, **sql.js can only execute SQLite syntax**, regardless of which dialect you picked. So:

- If you select **SQLite**, generation and live execution match exactly.
- If you select **MySQL** or **PostgreSQL**, QueryForge still generates correct dialect-specific SQL, and still attempts to run it against sql.js as a quick sanity check. If that query uses syntax SQLite doesn't understand (backtick identifiers, `ILIKE`, `SERIAL`, `RETURNING`, dialect-specific functions, etc.), the resulting error is caught and explained clearly — the app tells you live verification only reliably works for SQLite-compatible SQL, and that the query itself may still be correct for the dialect you chose. It never fails silently or crashes the UI.
- If a MySQL/PostgreSQL query happens to also be valid SQLite (many simple `SELECT` statements are), it will run successfully, and the results panel adds a note reminding you that behavior on the real target database may still differ for dialect-specific features.

## Groq request/response specification

**Request** (sent to `https://api.groq.com/openai/v1/chat/completions`):

```json
{
  "model": "llama-3.3-70b-versatile",
  "temperature": 0.2,
  "max_tokens": 2048,
  "response_format": { "type": "json_object" },
  "messages": [
    { "role": "system", "content": "…instructions + required JSON shape…" },
    { "role": "user", "content": "…dialect, schema, sample data, question…" }
  ]
}
```

**Expected response shape** (the JSON object inside `choices[0].message.content`):

```json
{
  "sql": "SELECT ...",
  "explanation": "A short plain-English explanation of what the query does and why.",
  "tables_used": ["customers", "orders"]
}
```

**Defensive parsing.** Real model output isn't always this clean, so `parseModelJson()` in `script.js` tries, in order:

1. Strip a ` ```json ... ``` ` (or plain ` ``` ... ``` `) fence if the whole response is wrapped in one.
2. Parse the (possibly unwrapped) text directly with `JSON.parse`.
3. If that fails, extract the substring between the first `{` and the last `}` (in case the model added a leading sentence or trailing commentary) and try parsing that.
4. If all of the above fail, throw a clear, specific error rather than silently showing nothing.

The parsed object is then validated: `sql` must be a non-empty string (otherwise the app throws before rendering anything), `explanation` defaults to a placeholder string if missing, and `tables_used` defaults to an empty array if it isn't a proper array.

## Configuration reference

All of these live as constants near the top of `script.js`:

| Constant | Purpose | Default |
|---|---|---|
| `API_KEY` | Your Groq API key | `"PASTE_YOUR_GROQ_API_KEY_HERE"` (placeholder) |
| `GROQ_API_URL` | Groq's chat completions endpoint | `https://api.groq.com/openai/v1/chat/completions` |
| `GROQ_MODEL` | Which Groq-hosted model to call | `llama-3.3-70b-versatile` |
| `SQL_JS_CDN_BASE` | Where sql.js's `.wasm` binary is fetched from | `https://cdnjs.cloudflare.com/ajax/libs/sql.js/1.5.0/` |
| `DIALECT_LABELS` | Maps dropdown values to human-readable dialect names | `{ sqlite: "SQLite", mysql: "MySQL", postgresql: "PostgreSQL" }` |

To use a different Groq model, change `GROQ_MODEL` to any model string listed at [console.groq.com/docs/models](https://console.groq.com/docs/models) that supports JSON mode — no other code changes are needed. To pin a different sql.js version, update `SQL_JS_CDN_BASE` and the matching `<script src="...">` tag in `index.html` together, since both must reference the same version.

## Error handling reference

| Scenario | Where it's caught | What the user sees |
|---|---|---|
| Empty schema on Generate | Client-side validation | "Paste your schema (CREATE TABLE statements) before generating." |
| Empty question on Generate | Client-side validation | "Type a question about your data before generating." |
| API key still the placeholder | Client-side validation | "No Groq API key set. Open script.js and paste your key into the API_KEY constant." |
| Groq returns HTTP 401 | Fetch response check | "Groq rejected the request: invalid API key. Check the API_KEY constant in script.js." |
| Groq returns HTTP 429 | Fetch response check | "Groq rate limit reached. Wait a moment and try again." (plus any detail Groq provides) |
| Groq returns HTTP 400 | Fetch response check | "Groq rejected the request: \<detail\>." |
| Any other non-2xx status | Fetch response check | "Groq API error (status \<code\>): \<detail\>." |
| Network failure (offline, DNS, CORS, etc.) | `TypeError` from `fetch()` | "Network error: couldn't reach the Groq API. Check your internet connection." |
| Model output isn't parseable JSON | `parseModelJson()` | "Couldn't parse a valid JSON object from Groq's response. The model may have replied in an unexpected format — try again." |
| Model output is missing a usable `sql` field | Response validation | "Groq's response was missing a valid \"sql\" field." |
| Run clicked before any query was generated | Client-side validation | "Generate a SQL query first before running it." |
| Run clicked with schema or sample data missing | Client-side validation | "Paste both your schema... and sample data... to run this query live." |
| Pasted schema fails to execute in sql.js | `db.run(schema)` catch | "Your CREATE TABLE statements couldn't be executed: \<sqlite error\>." |
| Pasted sample data fails to execute | `db.run(sampleData)` catch | "Your INSERT statements couldn't be executed: \<sqlite error\>." |
| Generated SQL fails in sql.js, non-SQLite dialect | `db.exec()` catch | "Live verification isn't fully compatible with this dialect" + an explanation that SQLite couldn't run the dialect-specific syntax, and that the query may still be correct |
| Generated SQL fails in sql.js, SQLite dialect | `db.exec()` catch | "SQL execution error: \<sqlite error\>." |
| sql.js itself fails to load | `ensureSqlJsLoaded()` | "sql.js failed to load from the CDN. Check your internet connection and reload the page." |

## Design system

The interface deliberately avoids gradient/glassmorphism marketing-page styling in favor of a restrained, single-accent look closer to real developer tools (GitHub, Linear, DataGrip).

**Color tokens** (all defined as CSS custom properties in `index.html`):

| Token | Value | Used for |
|---|---|---|
| `--ink-950` | `#0d1117` | Page background |
| `--ink-900` | `#12161d` | Panel background |
| `--ink-850` | `#161b22` | Inputs, code blocks, raised surfaces |
| `--ink-800` / `--ink-750` | `#21262d` / `#30363d` | Borders and dividers |
| `--paper` | `#e6edf3` | Primary text |
| `--muted` / `--faint` | `#8b949e` / `#565d68` | Secondary / tertiary text |
| `--accent` | `#2f81f7` | Primary buttons, focus rings, tags, links — the only accent color, used sparingly |
| `--signal-green` | `#3fb950` | Success states |
| `--signal-red` | `#f85149` | Error states |
| `--signal-amber` | `#d29922` | Warning / caveat states |

**Typography:** IBM Plex Sans for interface text and headings; IBM Plex Mono for all code, tags, status chips, and step numbers — one coherent type family rather than several unrelated ones.

**Shape:** 6–10px border radii, 1px borders, minimal shadow. No blurred background shapes or ambient animation; a static, near-invisible dot grid stands in for texture. The only in-flight motion is a thin top progress bar during generation/execution and small button spinners.

## Deploying to a Hugging Face Static Space

1. Go to [huggingface.co/new-space](https://huggingface.co/new-space), pick a name, and set the SDK to **Static**.
2. Add `index.html`, `script.js`, and `README.md` to the Space — either upload them through the web UI, or `git clone` the Space's repo, copy the three files in, then `git add`, `git commit`, and `git push`.
3. Paste your real Groq API key into `script.js`'s `API_KEY` constant, either before pushing or by editing the file directly in the Hugging Face web editor afterward.
4. The Space builds instantly since it's static — no build step, no secrets configuration needed, since the key lives in the client-side file.
5. **Tradeoff to keep in mind:** since this is fully static, the API key is visible to anyone who opens their browser's dev tools and looks at `script.js`. That's fine for a personal project or a private Space, but not appropriate for a public Space with real usage — anyone could read the key out of the page source and spend your Groq credits.

## Security considerations

- The Groq API key lives in plaintext in `script.js` and is sent from the browser on every "Generate SQL" click. Anyone with access to the deployed page's source can read it.
- Treat this project as suitable for **personal use or a private Space**. For a public deployment with real traffic, put the Groq call behind a small server-side proxy (even a single serverless function) that holds the key instead, and have the client call that proxy.
- No data is persisted anywhere — not in a database, not in browser storage. Refreshing the page clears everything. Query execution happens in an in-memory SQLite instance that's discarded after each run.
- Only the schema, sample data, and question you type are ever sent over the network (to Groq); actual query execution never leaves your browser.

## Known limitations

- Only a single active generation or execution runs at a time; there's no query history or persistence across page reloads.
- If the generated SQL contains multiple statements, only the last statement's result set is rendered.
- Live verification always runs against SQLite. Choosing MySQL or PostgreSQL gets you correctly generated dialect-specific SQL, but sql.js cannot independently confirm correctness for dialect-specific behavior (e.g. differing date/window functions, JSON operators, or types) — see [Dialect support and verification caveats](#dialect-support-and-verification-caveats).
- No authentication, multi-user support, or usage metering — this is a single-user, client-side tool by design.
- The Groq API key is visible in client-side source; see [Security considerations](#security-considerations).
